# Autoterm AIR 2D/4D: status codes (`major.minor`) and the error byte

Research for renewvan/hub issue 116. Question: what do the AIR 2D status codes and the error byte mean, and which errors need the `0x0D` unblock? Output is a table per row with source and confidence. Protocol facts only; nothing here is copied from the unlicensed upstream repo, and nothing was sent to a heater.

## Headline findings

1. **No manufacturer document publishes a `major.minor` status-code table.** The Autoterm manuals describe the start cycle in prose (self-test, glow-plug heating, ignition, run, purge) and the fault codes in tables, but never the wire status pairs. The only table of `major.minor` meanings is the community reverse-engineered upstream README (secondary, unlicensed, self-described "not complete nor immaculate"). So every status-code meaning is Low to Medium confidence at best, and the observed cycle is the strongest evidence we have.
2. **Error byte `0x1E` is 30 decimal.** Autoterm lists fault code **30** as "No communication between the controller and the control unit; control unit receives no data from the controller" (heading "Heater does not start"). On a heater driven by an external controller (our Pi standing in for the panel), this is exactly "the control unit stopped hearing the controller". Strong explanatory fit; the one inference is that the wire error byte equals the displayed fault code.
3. **`0x0D` unblock: the manufacturer documents an "Unlock" function but not which wire frame performs it, and not for 2D/4D explicitly.** Autoterm Test (the manufacturer's diagnostic program) has an Unlock button for "an air heater that was locked due to several failed ignition attempts in a row". The only manual lockout _codes_ are 33 (AIR-8D, three overheats) and 37 (Flow liquid heaters, three code-13 failures). The upstream README names a `0D` "Unlock" message but documents nothing about it (empty section). Mapping `0x0D` to that button is a reasonable inference, not a sourced fact.
4. **ADR 0021 has a real gap:** the observed cycle contains `2.0` and `2.6`, which the ADR's rule "any other code is `off`" would publish as `off` in the middle of a start. See "Implications for ADR 0021".

### Where the observed sequence supports or contradicts each source

- **Upstream (S5):** 9 of its 11 rows are order-consistent with the observation (0.1, 1.0, 1.1, 2.1, 2.2, 2.3, 2.4, 3.0, 4.0). It is silent on `2.0` and `2.6`, and the observed cycle shows both are routine. It orders `2.3` ("ignition 2") after `2.2`, matching what we saw, but a cold successful start still passes through ignition 2, so "ignition 1/2" is more likely stage names than "first and second attempt". Do not rely on the numeric suffix to mean attempt count.
- **ADR 0021:** The `1.x` conflict is mostly a naming issue, not a phase issue: both treat `1.0`/`1.1` as before ignition, and mapping them to `starting` is compatible with upstream's "cooling flame sensor" and "ventilation" (a pre-start purge). What should be recorded is that `1.x` is the pre-start purge, not a shutdown or run-state. The ADR's `3.4` as `shutting_down` is untested: in our cycle the shutdown purge was `4.0`, and `3.4` may be a different cooldown (for example after a fan-only/ventilation run or on a stop request in a particular state).
- **Manufacturer prose** gives the stage sequence (self-test, silent glow-plug heating, ignition, 100% warm-up, set mode, stop with purge) and the observed order matches it, but it never names wire codes. It supports the _order_, not the _labels_.

| Do ordinary errors need unlock?                   | No evidence they do. The panel clears a fault by "tapping the centre of the screen" (S3 sect. 8) and the heater is restartable otherwise. Practical reading: needing unblock is most plausibly "2 x code 13 per start, repeated until the heater locks" and, for AIR-8D only, "code 33". A 2D/4D that shows 13, 30, 16 and so on should be treated as errors that stop the heater, with unlock only if the heater refuses to start afterwards. The ADR's `clear_error` and unlock frames remain unverified, as the ADR already says.

## Implications for ADR 0021 (suggestions, not changes)

1. Add `2.0` and `2.6` to `starting`. Today they hit "any other code is `off`" and would flip the retained phase to `off` mid-start, which would also re-enable the "start from off" command path (`set true` starts only from `off`) while the heater is already igniting. Safer rule: treat unknown `2.x` as `starting`, or hold the previous phase and publish the raw `status_code`.
2. Keep `1.x` as `starting`, but describe it as the pre-start purge/sensor cooling, not ignition.
3. Keep `3.4` as `shutting_down` but mark it unverified; `4.0` is the observed shutdown stage (verified in S6 order).
4. Record error `30` (`0x1E`) as "link to the control unit lost" and keep `error_code` as the raw decimal.
5. Do not publish names like "ignition 2" in the UI; the suffix is a stage index, and a normal start passes through it.
