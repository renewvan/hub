# The broker has one account per client, anonymous read-only access, and the real browser gate sits in Caddy

_(The Caddy `basic_auth` gate is superseded by [ADR 0029](0029-dashboard-login-is-a-session-cookie.md): same gate, now a session cookie.)_

_(Superseded in part by [ADR 0026](0026-anonymous-clients-are-refused-after-the-cutover.md): after the cutover `allow_anonymous` is false and a read-only `reader` account replaces anonymous reads. The rest, per-client accounts and the Caddy gate, stands.)_

Mosquitto keeps `allow_anonymous true` on both listeners, but an ACL limits anonymous clients to `topic read renewvan/#`. Every client that writes has its own account in a password file: each driver (tank, gps, temperature, tilt, wattcycle, logger, venus, router, demo), each host plugin (kiosk, tailscale), the ESP32 relay node, and one `command` account for the dashboard. Username equals the client's topic key, so drivers share one `pattern write renewvan/%u/#` line. Only `command` may write the `set` topics (`relay/+/set`, `relay/+/name/set`, `kiosk/display/*/set`, heater `set` topics, `demo/enabled/set`). Everyone reads `renewvan/#`.

The `command` password reaches browsers through `/env.js`, so it is public. The gate for browsers is a shared Caddy `basic_auth` on `/mqtt` and `/influx` together (ADR 0024), with the kiosk's loopback path exempt. Caddy's 443 is bound to the van-LAN and Tailscale addresses, not all interfaces.

## Why

- **The tailnet and LAN may read; writing needs a credential.** Anyone who can reach 443 could otherwise switch a relay through the anonymous WebSocket, whatever the broker's own bind says.
- **Guests share the Pi's subnet,** so 1883 is reachable by them. A Caddy gate alone does not cover that path, hence per-client broker accounts.
- **One account per client keeps a leak small.** A leaked driver credential can spoof only that driver's topics; a leaked ESP32 credential cannot write `set` topics.
- **Keeping anonymous read matches the decision on reads** and avoids flipping `allow_anonymous` to false during cutover.

## Rejected alternatives

- **A few shared role accounts** (`driver`, `node`, `command`): easier to provision, but one leak spoofs every driver.
- **Anonymous off, with a read-only `viewer` account:** no client could read without a credential, and every node needs a restart on `rc=5`.
- **TLS on 1883 now:** the ESP32 needs a CA in firmware and its Arduino-framework clock behaviour is unverified. Deferred, not rejected.

## Rules this sets

- Denied publishes are silent on MQTT 3.1.1 and SUBSCRIBE is never refused, so the check script proves behaviour by its effect, never by an error.
- A client that sends credentials not in the password file is denied even with anonymous allowed (`rc=5`, needs a restart).
- A bad ACL line makes the broker exit on reload and `--test-config` does not check it, so deploy validates the ACL in a throwaway container before any SIGHUP.
- Credentials are generated by an idempotent `ensure-secrets` step. `bin/rotate-secret.sh <client>` rotates one client; the ESP32 is rotated only by OTA, on suspected compromise.
- Migration: bind 443, deploy accounts and ACL with a temporary `topic readwrite renewvan/#` line, move drivers and plugins then OTA the ESP32, confirm no anonymous publisher remains, remove the line and SIGHUP. Rollback restores the line.

## Accepted residual risk

Passwords on 1883 cross the van LAN in clear. A guest who sniffs one can write as that client, though never the `set` topics unless it is `command`'s (which is already public behind the Caddy gate). Revisit with TLS on 1883 when the ESP32 clock behaviour is verified.

## Why this is an ADR

Hard to reverse: every driver, plugin, node and the dashboard depend on the account layout. Surprising without context: a reader will wonder why anonymous clients can still read, and why the `command` password is public. The result of a real trade-off: stricter schemes (anonymous off, TLS now) cost nodes and reflashes for a threat the van's trust model only partly has.
